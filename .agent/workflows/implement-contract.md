# 스프린트 계약 구현 (Heavy 레인)

인자로 계약 파일 경로를 받는다. 예: `.harness/runs/<슬러그>/SPRINT_CONTRACT_2.md`
경로가 주어지지 않았다면 `.harness/runs/` 에서 가장 최근에 수정된 계약 파일을 찾아 **사람에게 확인받은 뒤** 진행한다.

## 1단계 — 컨텍스트 로드 (코드를 쓰기 전에)

다음을 순서대로 읽는다.

1. 루트 `AGENTS.md` — 저장소 정본
2. `.agent/rules/` 전체 — 가드레일
3. 지정된 `SPRINT_CONTRACT_<N>.md` — 이번에 할 일
4. 같은 디렉토리의 `SPEC.md` — 이 스프린트가 속한 전체 그림
5. 같은 디렉토리의 `QA_FINDINGS_<N-1>.md` (있다면) — 직전 QA 결함
6. 같은 디렉토리의 `HANDOFF.md` (있다면) — 함정·결정사항·환경 특이사항
7. 작업 성격에 맞는 `docs/*.md` (UI 작업이면 `ui-conventions.md` 는 필수)

**계약 §3 "성공 기준" 을 그대로 체크리스트로 옮겨 적는다.** 이것이 이번 작업의 완료 정의다.

계약 내용이 모호하거나 성공 기준이 검증 불가능한 문장이면, 구현을 시작하지 말고 **무엇이 모호한지 적어 사람에게 되묻는다.** 임의 해석으로 진행하지 않는다.

## 2단계 — 브랜치 확인

```bash
git status
git branch --show-current
```

- 현재 브랜치가 `feat/<슬러그>` 인지 확인한다. `main` 이면 중단하고 사람에게 알린다.
- 다른 도구가 남긴 미커밋 변경이 있으면 덮어쓰지 말고 사람에게 알린다.
- **새 브랜치를 만들지 않는다.** 계약과 함께 이미 준비된 브랜치에 커밋한다.

## 3단계 — 구현

- 계약 §1(구현 항목)과 §2(직전 QA 결함 수정)만 구현한다. **계약에 없는 개선을 임의로 끼워 넣지 않는다.**
- `.agent/rules/10-frontend.md` 의 토큰 우선·CSS Modules·FSD·별칭 규칙을 지킨다.
- 계약 범위 밖에서 발견한 문제는 고치지 말고 4단계의 기록 대상으로 남긴다.

## 4단계 — 정적 검증

```bash
pnpm build
pnpm --filter momozzang-invitation lint
pnpm --filter momozzang-admin lint
```

셋 다 통과할 때까지 진행하지 않는다. (`pnpm test` 는 이 저장소에 없다 — 호출하지 않는다.)

## 5단계 — 브라우저 검증 (이 워크플로의 핵심)

dev 서버를 띄운다.

```bash
pnpm dev:invitation     # 뷰어
pnpm dev:admin          # 어드민 (port 3002)
```

계약 §3 의 성공 기준을 **하나씩 브라우저에서 직접 수행**한다. 코드를 읽고 "통과할 것이다" 라고 판단하지 않는다. 실제로 클릭하고 입력하고 스크롤한다.

- 기준마다 **스크린샷을 남기고, 계약 파일과 같은 디렉토리에 저장**한다.
  - 경로 규칙: `.harness/runs/<슬러그>/shots/s<N>-<기준번호>-<짧은설명>.png`
  - 예: `.harness/runs/apply-form-preview/shots/s2-1-preview-open.png`
- 이 프로젝트는 모바일 청첩장이다. **모바일 뷰포트(375×812 기준)로 확인**한다.
- 실패한 기준은 3단계로 돌아가 고친다. 실패를 통과로 적지 않는다.

## 6단계 — 계약 §5 자가 점검 표 작성

계약 파일의 "5. 생성자 자가 점검" 표를 채운다.

| 기준 | 자가 점검 결과 | 확인 방법 |
|------|----------------|-----------|
| 1 | ✅ / ❌ | 브라우저에서 실제로 한 조작 + 스크린샷 경로 |

- "확인 방법" 은 반드시 **실제로 수행한 조작**을 적는다. "코드상 문제없음" 은 확인 방법이 아니다.
- 통과하지 못한 기준은 ❌ 로 남기고 이유를 적는다. **숨기지 않는다.**
- 표 아래 "비고" 에 다음을 기록한다.
  - 구현 중 내린 주요 결정과 그 이유
  - 알려진 한계
  - 계약 범위 밖에서 발견했지만 고치지 않은 문제
  - 다음 사람이 파일만 읽어서는 알 수 없는 함정(포트 충돌, 환경 특이사항 등)

## 7단계 — 커밋 + 인수인계

```bash
# 변경한 소스 경로 + 계약 파일 + 스크린샷만 명시적으로 스테이징한다
git add <변경한 소스 경로들> .harness/runs/<슬러그>/SPRINT_CONTRACT_<N>.md .harness/runs/<슬러그>/shots/
git status                      # 의도한 파일만 올라갔는지 확인
git commit                      # .agent/rules/20-git.md 의 한글 feat:/fix: 컨벤션을 따른다
```

> **`git add -A` / `git add .` 를 쓰지 않는다.** 이 저장소의 워킹 트리에는 다른 도구가 남긴 로그·프로브 스크립트 등 추적되지 않는 파일이 상시 존재한다. 전체 스테이징은 그것들을 기능 커밋에 쓸어 담는다.

- 계약 파일(§5 채운 것)과 스크린샷을 **코드와 함께 커밋**한다. 이것이 다음 단계의 입력이다.
- `HANDOFF.md` 를 갱신한다(템플릿: `.harness/templates/HANDOFF.md`).
  - 현재 상태 한 줄 / 마지막 커밋 해시 / **바로 다음 할 일 = "Claude Code 에서 e2e-tester 로 독립 QA"** / 함정
- **push 하지 않는다.** push 와 PR 은 Claude Code 의 `/pr` 이 담당한다.

## 8단계 — 사람에게 보고

다음 형식으로 짧게 보고하고 끝낸다.

```
계약: SPRINT_CONTRACT_<N>.md
성공 기준: N개 중 M개 통과 (미통과: <번호와 사유>)
커밋: <해시> <메시지>
스크린샷: .harness/runs/<슬러그>/shots/
다음: Claude Code 창에서 e2e-tester 로 독립 QA 를 돌리세요.
```
